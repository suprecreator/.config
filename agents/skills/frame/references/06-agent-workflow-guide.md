# AI 代理的 Shape Up：工作流程指南

> 使用 AI 代理系统实施 Shape Up 方法论的主要参考手册。将 Shape Up 角色和流程映射到代理能力。

---

## Shape Up 角色映射到代理

| Shape Up 角色 | 代理类型 | 职责 |
|--------------|---------|------|
| **框架化者** | 框架化代理 | 调查原始想法。缩小问题范围，评估商业价值，产出框架文档。关卡：框架通过。（参见 `08-framing.md`） |
| **塑形者** | 塑形代理 | 将已框架化的问题转化为方案包。寻找元素，通过代码库分析去风险，撰写方案包。关卡：塑形通过。 |
| **押注桌** | 协调者/人类 | 决定将哪些方案包提交资源。需要人类判断进行战略优先级排序。 |
| **构建者（设计师）** | 设计代理 | 创建功能点、UI 结构、交互流程。首先在面包板级别工作，之后细化。 |
| **构建者（程序员）** | 编码代理 | 实现后端，连接功能点，部署。构建战略性不完整的脚手架。 |
| **QA** | 验证代理 | 在已完成的范围中寻找边缘情况。所有发现默认为可选项。 |

---

## 代理工作流程：完整流程

### 塑形轨道

**警告：#1 失败模式是塑形不足的工作。参见 `07-pitfalls.md`。**

```
流程：候选项 → 框架通过 → 塑形通过 → 押注 → 构建 → 交付

1. 接收
   代理接收原始想法或功能请求。
   默认立场："有意思，也许以后会做。"——不要承诺。
   状态：候选项

2. 框架化（问题 + 商业价值，而非解决方案）——参见 08-framing.md
   → 调查：实际痛点是什么？谁受影响？哪个用户群？
   → 量化：多少用户，多频繁，什么收入/留存影响？
   → 评估：这是否与当前优先级一致？现在是正确时机吗？
   → 缩小：从通用请求 → 具体、可观察的痛点
   → 设定时间预算：Small Batch（1 个会话）/ Medium Batch（2-3 个会话）/ Big Batch（4-5 个会话）
   → 拒绝大杂烩：没有没有单一定义问题的"重新设计 X"
   → 产出框架文档（参见 08-framing.md 中的模板）
   → 检查点：呈现给人类。"这值得投入塑形时间吗？"
   状态：框架通过

3. 元素（具有技术深度）
   → 面包板：定义场所、功能点、连接（用于流程）
   → 粗笔草图：粗略的空间布局（用于视觉问题）
   → 输出：连接——事物如何连接，数据流向哪里，哪些代码受影响
   → 不仅仅是 UI 概念。必须描述蓝图，而非渲染效果。

4. 去风险（不允许有 TBD）
   → 审查实际代码库、数据模型、现有架构
   → 逐步走过用例
   → 对每个元素：在时间预算内技术上可行吗？
   → 应用：声明超出范围 / 缩减 / 修补漏洞
   → 每个兔子洞必须有解决方案。未解决 = 定时炸弹。
   → 检查点：构建者能接手并知道该做什么吗？
   状态：塑形通过

5. 方案包（"提案"的演进术语）
   → 撰写包含 5 个要素的文档：
     问题 | 时间预算 | 解决方案 | 兔子洞 | 排除项
   → 这不是销售提案——业务方在框架通过时已经认可
   → 这是所有项目变量的完整方案包
   → 提交给押注桌进行最终审批
```

### 构建轨道

**警告：永远不要将响应性工作混入构建会话。参见 `07-pitfalls.md`。**

```
会话 1：定向 + 第一个部分
├── 研究方案包，探索代码库，确定方法
├── 选择第一个部分（核心 + 小 + 新颖）
├── 垂直集成第一个部分（UI + 后端）
└── 里程碑：一个可点击的、工作的部分

会话 1-2：映射范围
├── 通过实际工作发现范围（而非提前计划）
├── 用项目特定语言命名范围
├── 分类任务：必须项 vs. 可选项（~）
└── 验证：可以看到整个项目吗？范围名称感觉自然吗？

中间会话：执行 + 追踪
├── 首先将最有风险的范围推上坡
├── 用真实代码验证方法（而非理论）
├── 更新每个范围的山丘图位置
├── 持续范围锤炼：质疑每个新任务
└── 优先级：未知因素优先，常规工作最后

最后会话：收敛 + 交付
├── 所有范围应该在下坡
├── 积极范围锤炼：删除任何非必须项
├── 与基线比较：这比现有的更好吗？
├── 部署
└── 不要承诺交付后反馈
```

### 响应性工作分类（与构建分开运行）

构建期间的传入工作在行动前必须分类：

```
传入项目 →
  这是已塑形的、已押注的项目吗？
    是 → 构建工作。在分配的会话内执行。
  这是活跃事故/系统宕机/利益相关者不满吗？
    是 → 紧急。在单独的容量上处理（看板）。单独追踪。
  这是不紧急的错误吗？
    否 → 批量处理以后。不要混入活跃构建。
  这依赖于第三方响应吗？
    是 → 单独追踪。你无法控制时间线。
```

永远不要让响应性工作悄悄消耗会话时间。如果它在吃掉构建时间，明确提出并调整范围。

### 构建后

```
1. 将所有反馈视为原始想法
2. 不要承诺变更
3. 重要反馈 → 进入塑形轨道
4. 不重要反馈 → "有意思，也许以后会做。"
```

## 代理决策规则

### 塑形时

| 情况 | 规则 |
|------|------|
| 想法模糊 | 在继续之前缩小到具体痛点 |
| 想法对 5 个会话来说太大 | 分解为独立部分 |
| 想法是大杂烩（"重新设计 X"） | 拒绝。要求具体的问题陈述。 |
| 技术可行性不确定 | 在时间预算内验证，而非抽象地验证 |
| 找不到简单解决方案 | 削减范围，而非时间线。时间预算是固定的。 |
| 存在多种方法 | 选择在时间预算内未知因素最少的那个 |

### 构建时

| 情况 | 规则 |
|------|------|
| 不知道从哪里开始 | 选择最核心、最小、最新颖的部分 |
| 任务看起来必要但不核心 | 应用范围锤炼问题。可能是可选项。 |
| 范围在山丘图上卡住 | 拆分为更小的范围或调查未知因素 |
| 发现新需求 | 默认：可选项。只有在真正关键时才提升。 |
| 时间用完 | 删除可选项。交付必须项。与基线比较。 |
| 最后会话时工作仍在上坡 | 塑形失败。不要延期。返回塑形。 |
| QA 发现问题 | 默认可选项。按严重性分类。 |
| 交付后反馈到来 | 原始想法。不要承诺。如果重要则塑形。 |

### 进展评估

| 信号 | 健康状态 | 行动 |
|------|---------|------|
| 会话 1：第一个部分已集成 | 健康 | 继续 |
| 会话 1-2：范围已映射，最有风险的在上坡 | 健康 | 将风险推过山丘 |
| 中期构建：最有风险的范围在下坡 | 健康 | 执行剩余范围 |
| 中期构建：大多数范围在下坡 | 健康 | 开始收敛 |
| 最后会话：一切在下坡 | 健康 | 润色并交付 |
| 会话 2：尚无集成部分 | 警告 | 调查阻碍 |
| 中期构建：范围仍卡在上坡 | 危险 | 拆分范围，范围锤炼 |
| 最后会话：范围仍在上坡 | 危急 | 无法延期。塑形失败。 |

## 代理的关键约束

1. **永远不要延长时间线。** 时间预算是固定的。只有范围灵活调整。
2. **永远不要承诺未经验证的方法。** 用代码验证，而非理论。
3. **永远不要接受大杂烩。** 每个项目都需要具体的问题。
4. **永远不要跳过去风险。** 在构建之前走过用例。
5. **永远不要按角色组织。** 按范围组织（独立的、可完成的单元）。
6. **永远不要从外围功能开始。** 从核心 + 小 + 新颖开始。
7. **永远不要估算任务。** 追踪不确定性（山丘位置），而非小时数。
8. **可选项是压力阀。** 自由地用 `~` 标记。自由地删除。
9. **与基线比较，而非理想状态。** 当比今天更好时交付，而非当完美时。
10. **反馈是原材料。** 永远不要承诺交付后的变更。先塑形它们。
11. **永远不要在没有技术深度的情况下塑形。** 审查实际代码、数据模型、架构。连接，而非样式。（#1 失败模式——参见 `07-pitfalls.md`）
12. **永远不要在框架化之前塑形。** 在设计解决方案之前锁定问题。候选项 → 框架通过 → 塑形通过。
13. **永远不要将兔子洞留为 TBD。** 每个未解决的兔子洞都会在构建期间爆炸。修补、缩减或声明超出范围。
14. **永远不要将响应性工作混入构建会话。** 错误、事故和依赖第三方的工作是具有单独追踪的独立流。

## 押注桌输入格式

在呈现方案包进行押注决策时：

```
方案包：[项目名称]
问题：[一句话痛点]
用户群：[谁受影响，多少人，商业价值]
时间预算：[Small Batch 1 个会话 / Medium Batch 2-3 个会话 / Big Batch 4-5 个会话]
解决方案：[关键元素，2-3 句话——连接，而非样式]
已处理的风险：[兔子洞如何处理——零 TBD]
排除项：[不包含什么]
框架状态：框架通过（于[日期/由谁]批准）
塑形状态：塑形通过（所有未知因素已解决）
```

## 山丘图状态格式

报告进展时：

```
构建：[名称] — 第 [X] 个会话，共 [N] 个

范围：
  ▲ [范围名称] — 上坡（调查方法）
  ▲ [范围名称] — 上坡（已验证，接近顶峰）
  ▼ [范围名称] — 下坡（执行已知工作）
  ▼ [范围名称] — 下坡（接近完成）
  ✓ [范围名称] — 完成（已部署）
  ~ [范围名称] — 可选项（如需要可删除）

风险：[最有风险的范围及其状态]
下一步：[团队接下来要推上坡的内容]
```
