# 方案包模板（原"提案"）

> AI 代理撰写或评估方案包的参考手册。方案包是在押注桌上呈现的已塑形产物。它包含所有必要的项目变量：问题、解决方案、时间、风险和边界。
>
> **术语说明**：Ryan Singer 将术语从"Pitch（提案）"演进为"Package（方案包）"，因为业务方在框架化阶段已经认可。塑形的输出不再是销售提案——而是准备好进行构建承诺的完整方案包。参见 `08-framing.md` 了解此前的框架化步骤。
>
> **前提条件**：方案包只应在**框架通过**之后撰写——业务方已确认问题值得解决并授权塑形时间。

## 结构

每个方案包必须包含恰好五个要素。不多不少。

---

## 1. 问题

**是什么**：展示当前情况为何对用户失败的具体、真实故事。

**要求**：
- 描述单一、具体的场景（而非一般性抱怨）
- 展示基线：用户今天在没有此功能的情况下是怎么做的
- 使痛点具体且可观察
- 将"这个问题值得解决吗？"与"这个解决方案好吗？"分开

**测试**：有人读了这个能理解为什么当前情况是不可接受的吗？他们能根据这个具体的痛点评估任何提议的解决方案吗？

**示例格式**：
```
当[特定用户类型]尝试[特定操作]时，他们必须[当前痛苦的变通方法]。
这导致[特定负面结果]。目前[X 个用户 / Y% 的情况]会遇到这个问题。
```

---

## 2. 时间预算

**是什么**：时间预算——这个问题值得投入多少时间。

**选项**：
- **Small Batch（小批次）**：1 个会话
- **Medium Batch（中批次）**：2-3 个会话
- **Big Batch（大批次）**：4-5 个会话

**要求**：
- 明确陈述时间预算
- 时间预算约束解决方案——不同的时间预算产生不同的设计
- 一旦设定，时间预算不可协商

**示例格式**：
```
时间预算：[Small Batch — 1 个会话] 或 [Medium Batch — 2-3 个会话] 或 [Big Batch — 4-5 个会话]
```

---

## 3. 解决方案

**是什么**：在时间预算内解决问题的已塑形元素。

**要求**：
- 描述关键元素（组件，而非任务）
- 使用嵌入式草图或注释粗笔草图提供视觉上下文
- 保持粗糙——不使用线框图，不使用像素级精确的模型
- 展示新元素在现有系统中的位置
- 包含足够的细节让团队理解方法
- 留有足够的模糊性让团队做出执行决策

**可视化规则**：
- 将新元素放置在现有 UI 的上下文中
- 仅使用粗笔草图级别的细节
- 添加清晰的标签和注释
- 添加免责声明："设计师可以自由寻找不同的方法"
- 只可视化需要具体理解才能"理解"想法的部分

**示例格式**：
```
解决方案引入了[关键元素 1]、[关键元素 2]和[关键元素 3]。

[元素 1]出现在[系统中的位置]，允许[什么操作]。
[元素 2]通过[如何]连接到[元素 1]。
[元素 3]处理[什么情况]。

[嵌入式草图或注释粗笔草图]
```

---

## 4. 兔子洞

**是什么**：已知风险、技术未知因素及其处理方式。

**要求**：
- 列出每个已识别的风险
- 对于每个风险：说明如何解决、缩减范围或声明超出范围
- 指出团队应尽早验证的假设
- 注明为降低风险而选择的简化实现

**示例格式**：
```
- [风险 1]：通过[决策]解决。我们选择了[更简单的方法]而非[复杂方法]。
- [风险 2]：声明超出范围。[用例 X]在此版本中不受支持。
- [风险 3]：团队应尽早验证[假设]。如果不成立，备选方案是[替代方案]。
```

---

## 5. 排除项

**是什么**：明确列出不包含的内容。故意排除的功能、用例和范围。

**要求**：
- 清楚列出每个排除项
- 简要说明原因（防止在构建期间重新讨论该决策）
- 这些是边界，而非未来计划

**示例格式**：
```
- 不包含[功能 X]：[原因——对时间预算来说太复杂 / 不是问题的核心 / 可以稍后添加]
- 不包含[用例 Y]：[原因——影响用户太少 / 需要尚不可用的基础设施]
- 不包含[能力 Z]：[原因——会将范围扩展超出时间预算]
```

## 提案评估检查清单

AI 代理评估提案是否准备好进入押注桌：

### 完整性
- [ ] 问题是具体的、基于故事的（而非通用的）
- [ ] 时间预算已明确陈述
- [ ] 解决方案描述了具体元素（而非模糊功能）
- [ ] 兔子洞已识别并处理
- [ ] 排除项定义了清晰的边界

### 质量
- [ ] 问题和解决方案是可分离的（可以独立评估每个）
- [ ] 解决方案符合所述时间预算
- [ ] 解决方案是粗糙的（未过度规定）
- [ ] 解决方案是已解决的（主要元素在宏观层面相互连接）
- [ ] 解决方案是有边界的（范围有清晰限制）
- [ ] 兔子洞已去风险（修补、缩减或声明超出范围）
- [ ] 在时间预算内验证了技术可行性

### 押注桌问题
- [ ] 这个问题值得花[时间预算]吗？
- [ ] 时间预算对这个问题合适吗？
- [ ] 考虑到约束，解决方案有吸引力吗？
- [ ] 现在是构建这个的正确时机吗？
- [ ] 合适的人员是否可用？

```markdown
# [项目名称]

## 问题
[关于用户痛点和当前基线的具体故事]

## 时间预算
[Small Batch — 1 个会话] 或 [Medium Batch — 2-3 个会话] 或 [Big Batch — 4-5 个会话]

## 解决方案
[带注释草图的关键元素描述]

### 元素：[名称]
[它是什么，适合放在哪里，它能实现什么]

### 元素：[名称]
[它是什么，适合放在哪里，它能实现什么]

## 兔子洞
- [风险]：[解决方案]
- [风险]：[解决方案]

## 排除项
- [排除项]：[原因]
- [排除项]：[原因]
```
