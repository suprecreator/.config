# 框架化

> AI 代理执行框架化角色的参考手册。框架化是塑形之前的正式步骤，锁定问题、评估商业价值并授权投入塑形。

来源：Ryan Singer，"框架化"（2022 年 4 月）——基于实际应用的 Shape Up 演进。

---

## 为何存在框架化

原版 Shape Up 书将押注桌放在塑形之后。这产生了一个问题：塑形者无法在不知道业务是否重视该问题的情况下，证明花时间进行严格技术塑形是合理的。结果是**塑形不足的工作**——推销想法但缺乏技术严谨性的提案，导致构建失控。

框架化通过在塑形开始之前建立业务承诺来解决这个问题。它将两个不同的问题分开：

1. **框架化**："这个问题值得投入时间寻找解决方案吗？"
2. **塑形**："在时间预算内适合的技术解决方案是什么？"

---

## 什么是框架化

框架化是挑战问题、缩小范围并确定业务是否有兴趣和紧迫性来解决它的工作。

它**不是**：
- 将项目拖上拖下优先级列表
- 对功能请求说是或否
- 撰写解决方案或设计任何东西

它**是**：
- 深入挖掘请求真正意味着什么
- 识别谁真正受影响
- 评估现在是否是正确的时机
- 量化商业价值和机会
- 将问题缩小到具体且可行动的内容

## 框架化会话中发生什么

框架化会话涉及塑形者和产品/业务人员共同调查问题。

### 需要回答的问题

- **哪个客户群受影响？**
- **与其他群体相比，这个群体有多有价值？**
- **业务中还有什么其他事情在竞争注意力？**
- **什么数据支持（或反驳）紧迫性？**
- **实际痛点 vs. 所述功能请求是什么？**
- **现在是正确的时机，还是有依赖或阻碍？**

### 活动

- 调取客户研究数据
- 运行查询以量化问题（受影响的用户数量、频率、收入影响）
- 审查过去的反馈和支持工单
- 检查客户群及其战略重要性
- 挑战关于紧迫性和价值的假设

### 输出

一个**框架良好的问题**，可以表述为：

> "如果我们能将其塑形为可行的并在 [N 个会话] 内执行，那对我们来说将是有意义的。"

这是**承诺花时间塑形**，但**尚未承诺构建**。

## 修订后的流程

原书的流程是：

```
原始想法 → 塑形 → 提案 → 押注桌 → 构建
```

演进后的流程是：

```
原始想法 → 框架化 → [框架通过] → 塑形 → 方案包 → [押注桌] → 构建
```

### 阶段定义

| 阶段 | 输入 | 工作 | 输出 | 关卡 |
|------|------|------|------|------|
| **候选项** | 原始想法、功能请求、投诉 | 尚无 | — | — |
| **框架化** | 候选项 | 问题调查、商业价值分析、用户群分析 | 带时间预算的框架良好的问题 | **框架通过**：业务说"这很重要，投入塑形" |
| **塑形** | 已框架化的问题 | 技术解决方案设计、去风险、代码库分析 | 方案包（问题 + 解决方案 + 时间预算 + 兔子洞 + 排除项） | **塑形通过**：解决方案可行，所有未知因素已解决 |
| **押注桌** | 方案包 | 战略评估 | 押注或放弃 | **押注**：承诺分配的会话 |
| **构建** | 已押注的方案包 | 执行 | 已部署的软件 | 交付 |

### 术语更新

| 旧术语（书中） | 新术语（演进后） | 原因 |
|--------------|---------------|------|
| 提案 | **方案包** | 塑形输出不再是销售提案——它是所有变量（问题、解决方案、时间、风险、边界）的完整方案包。业务方在框架化时已经认可。 |
| （第 3 章中隐含） | **框架化** | 现在是一个命名的、明确的步骤，有自己的会话、参与者和审批关卡。 |

"提案"更好地描述了**框架化的输入**——有人倡导某个问题值得关注。**塑形的输出**是方案包：为项目汇集在一起的所有必要变量。

## AI 代理的框架化

### 为何代理需要这个

给定功能请求的代理会默认立即设计解决方案。没有框架化，代理：
- 塑形业务可能不重视的工作
- 产出与业务上下文脱节的解决方案
- 无法做出智能的范围权衡（不知道哪个客户群重要或为什么）
- 面临"闪亮物体"失败的风险——在构建中途被取消的工作，因为从来没有真正的信念

### 代理框架化协议

当代理收到原始想法或功能请求时：

```
1. 分类为候选项
   → 还不要设计任何东西

2. 调查问题
   → 实际痛点是什么？（而非所述的功能请求）
   → 谁受影响？哪个用户群？
   → 多少用户 / 多频繁 / 什么收入影响？
   → 什么数据支持或反驳紧迫性？
   → 基线是什么——用户今天如何应对？

3. 评估业务一致性
   → 这是否与当前战略优先级一致？
   → 还有什么在竞争注意力？
   → 现在是正确的时机吗？

4. 缩小问题
   → 从通用请求 → 具体、可观察的痛点
   → 拒绝大杂烩（必须是单一问题）

5. 设定时间预算
   → 这值得多少个会话？（Small Batch 1 个会话 / Medium Batch 2-3 个会话 / Big Batch 4-5 个会话）
   → 时间预算约束下游的一切

6. 产出框架文档
   → 问题陈述（具体、基于故事）
   → 受影响的用户群和商业价值
   → 时间预算
   → 陈述："如果我们能在 [N 个会话] 内构建 [X]，它将 [业务结果]"

7. 请求框架通过
   → 向人类决策者呈现框架
   → 关卡："这值得投入塑形时间吗？"
   → 只有在批准后才继续塑形
```

### 框架文档模板

```markdown
# 框架：[简短名称]

## 问题
[展示痛点的具体故事。谁受影响，发生了什么，当前的变通方法是什么。]

## 受影响的用户群
[哪些用户/客户。多少人。有多有价值。]

## 商业价值
[如果我们解决这个问题会发生什么变化。收入、留存、效率、战略定位。]

## 证据
[量化问题的数据点、查询结果、支持工单数量、客户引用——任何量化问题的内容。]

## 时间预算
[Small Batch（1 个会话）/ Medium Batch（2-3 个会话）/ Big Batch（4-5 个会话）]

## 框架陈述
"如果我们能将其塑形为可行的并在 [N 个会话] 内执行，它将 [具体业务结果]。"

## 状态：候选项 / 框架通过 / 已拒绝
```
