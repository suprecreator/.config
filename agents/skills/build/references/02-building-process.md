# 构建过程

> AI 代理执行构建角色的参考手册。构建在固定的会话时间预算内执行已塑形的工作。

## 概述

构建在方案包被押注后开始。构建者接收完整的项目——而非单个任务。构建者拥有在已塑形边界内如何执行的所有决策权。构建以部署的软件结束。

---

## 阶段 1：定向（第 1-3 天）

### 发生什么

- 团队研究提案、现有代码库和系统
- 每个成员确定起点和方法
- 不产生可见输出——这是正常且必要的

### 规则

- **不要打扰**定向期间的团队
- **不要询问状态**或要求可见进展
- **三天规则**：如果沉默持续超过三天，则进行检查

### 输出

- 团队已确定第一个要集成的部分

---

## 阶段 2：完成一个部分（第 3-7 天）

### 第一个部分的选择标准

第一个部分必须是：

1. **核心** ——项目概念的中心。没有它，其他工作就没有意义。
2. **小** ——几天内可以完成。创造动力。
3. **新颖** ——如果两个部分同样核心且小，优先选择从未做过的那个。消除不确定性。

**不要从以下开始**：登录系统、项目设置、基础设施或任何外围内容。

### 垂直集成

对这一个部分跨所有层完全集成：

```
错误：完成所有设计 → 完成所有后端 → 最后集成
正确：设计一个部分 → 连接到后端 → 可以点击的工作功能
```

### 执行模式

1. **设计师**：创建基本功能点（按钮、字段、布局）——不是像素级完美。普通 HTML，默认颜色，足够的视觉层次。
2. **程序员**：构建足够的后端使功能点可用。战略性脚手架——路由、部分模型、需要时使用模拟数据。
3. **来回迭代**：轮流叠加功能点、代码和样式。每轮后点击查看进展。

### 优先顺序

1. 功能点（用户可以与什么交互？）
2. 连接到后端（它实际上能工作吗？）
3. 文案和布局（它可以理解吗？）
4. 视觉样式（它看起来对吗？）

### 后端策略

构建**战略性不完整**的后端：
- 渲染模板但尚无模型的控制器
- 在屏幕之间导航的路由，即使不是全部连接
- 尚不需要真实实现的地方使用硬编码值或模拟数据
- 如果测试需要，使用最简单的身份验证（例如，带硬编码密码的 HTTP 基本认证）

### 里程碑

到第一个会话结束：项目的一个集成的、可点击的部分端到端工作。建立信心。验证概念。

---

## 阶段 3：映射范围（会话 1-2）

### 什么是范围

范围是项目中可以独立构建、集成和完成的部分。它们是：
- 比单个任务大
- 比项目小得多
- 项目的工作词汇

### 发现过程

范围是**通过实际工作发现的**，而非提前计划的。

1. 从捕获发现的任务开始
2. 随着工作揭示关系，将任务分组为范围
3. 用特定于此项目的语言命名每个范围
4. 预期范围在会话 1 或会话 2 开始时稳定
5. 随着真实边界出现，预期会有重新排列和重命名

### 范围质量检查

**好的范围具有：**
- [ ] 可以在宏观层面看到整个项目
- [ ] 对话自然地使用范围名称
- [ ] 新任务容易归类到现有范围

**坏的范围表现为：**
- [ ] 难以说清楚范围何时"完成" → 内部任务不相关，将其分解
- [ ] 名称对项目不唯一（例如，"前端"、"错误"、"杂务"）→ 大杂烩，不是真正的范围
- [ ] 太大，无法很快完成 → 拆分为更小的部分

### 范围模式

| 模式 | 描述 | 策略 |
|------|------|------|
| **层叠蛋糕** | 均匀的 UI 和后端工作 | 通过 UI 表面积估算。信息系统的默认模式。 |
| **冰山** | 后端远超 UI（或反之） | 将 UI 分解为单独的范围。将后端拆分为独立部分。 |
| **倒置冰山** | UI 远超后端 | 质疑复杂性是否必要。如果可能，简化。 |
| **杂烩** | 不适合任何地方的零散任务 | 保留一个列表，最多 3-5 项。如果更长，其中隐藏着一个范围。 |

### 可选项标记

用 `~` 前缀标记任务以表示可选状态：
- `~ 优化加载动画`
- `~ 处理空状态的边缘情况`
- `~ 重构数据层`

如果时间用完，可选项无需愧疚地删除。它们是范围管理的主要工具。

整个范围也可以标记为可选项。

## 阶段 4：用山丘图追踪进展

### 山丘模型

所有工作经历两个阶段：

```
        ↗ 上坡 ↗          ↘ 下坡 ↘
   （未知，摸索中）  （执行，已知工作）

开始 ──────── 顶峰 ──────── 完成
```

### 上坡子阶段

1. **前三分之一**："我已经思考过这个"
2. **中间三分之一**："我已经验证了我的方法"
3. **最后三分之一**："我已经构建了足够多，确认没有剩余未知因素"

**关键规则**：只有在用实践验证后，才能将范围移到山丘顶部，而非仅凭思考。基于理论的信心（"我只需使用那个 API"）在实践中经常崩溃。

### 使用山丘图

- 将每个范围绘制为山丘上的一个点
- 定期更新位置
- 比较过去的状态以查看移动情况
- 不移动的点 = 可能卡住的警示信号

### 卡住范围协议

当范围在山丘图上似乎卡住时：

1. 探究什么是未知的或阻碍进展的
2. 检查范围是否画得太宽
3. 如果范围包含处于不同阶段的不相关部分 → **将其拆分**为更小的范围
4. 重构后，各个部分独立移动

### 工作排序规则

1. **最先处理最有风险的范围** ——在其他任何事情之前将最可怕的未知因素推上坡
2. **优先级问题**："如果时间用完，哪个范围可以尽管有未知因素也能拼凑完成？哪个可能比预期更难？"
3. **倒金字塔**：最重要的问题优先，最多未知因素优先。将常规工作留到最后。
4. 到最后一个会话：重要的事情已完成，只剩可选项。

---

## 阶段 5：决定何时停止

### 与基线比较，而非理想状态

- **错误的问题**："这是最好的版本吗？"
- **正确的问题**："这比客户今天拥有的更好吗？"

基线（客户现在如何解决问题）是比较点。当改进明显时交付，而非当达到完美时。

### 范围锤炼

持续质疑每项工作：

| 问题 | 目的 |
|------|------|
| 这对新功能是必须的吗？ | 核心 vs. 外围 |
| 没有这个我们能交付吗？ | 必要性测试 |
| 如果我们不做这个会怎样？ | 影响评估 |
| 这是新问题还是已有问题？ | 范围边界 |
| 这种情况发生的可能性有多大？ | 概率过滤 |
| 哪些客户会看到它？有多少？ | 受众过滤 |
| 它是核心（所有人）还是边缘情况？ | 优先级过滤 |
| 实际影响是什么？ | 严重性评估 |

### 必须项 vs. 可选项

- **必须项**：任务保留在范围内。范围在任务完成之前不算完成。
- **可选项**（`~`）：如果时间允许则完成。无需愧疚地删除。通常永远不会构建。

### QA 集成

- QA 在最后一个会话临近时进入，寻找边缘情况
- 所有 QA 发现的问题**默认为可选项**
- 团队进行分类，只有在真正关键时才提升为必须项
- 设计师和程序员负责基本质量——QA 是提升，而非关卡

### 延期标准

延期**非常罕见**，需要同时满足两个条件：

1. 未完成的任务是经过范围锤炼后仍存活的真正必须项
2. **所有**剩余工作都是下坡的（没有未知因素，只有执行）

如果在最后一个会话时工作仍在上坡 → 塑形问题。返回塑形，不要延期。

---

## 阶段 6：交付并继续前进

### 部署

- 完成意味着已部署。不是"准备好审查"或"在暂存环境中"。
- 小批次项目在单个会话内交付
- 测试和 QA 在构建会话内进行，而非之后

### 交付后规则

1. **让反馈风暴过去** ——给它几天时间。不要对初始噪音做出反应。
2. **保持无债务** ——不要根据初始反馈承诺变更。保持干净的状态。
3. **反馈需要塑形** ——将所有交付后的反馈视为原始想法。它们像任何其他想法一样进入塑形过程。
4. **不立即承诺** ——对立即承诺说"不"保留了未来的自由。"是"创造了债务。

### 反馈处理

```
交付后反馈到来
  → 视为原始想法（而非承诺）
    → 如果真正重要 → 在塑形轨道上塑形它
      → 在下次押注桌上竞争
        → 如果被押注 → 在未来会话中构建
```

---

## 反模式

| 反模式 | 为何失败 |
|--------|---------|
| 分配单个任务 | 使团队与大局脱节。对现实视而不见。 |
| 提前计划所有任务 | 想象的任务 ≠ 发现的任务。计划将会出错。 |
| 水平分层（所有设计，然后所有代码） | 直到最后才有任何集成。后期失败风险高。 |
| 从外围功能开始 | 延迟了解核心概念。在非必要事项上浪费时间。 |
| 连接之前进行像素级完美设计 | 如果方法不起作用，浪费了努力。 |
| 按角色组织范围 | 隐藏了真实的项目结构。阻止看到大局。 |
| 用上坡工作延期项目 | 截止日期时的未知因素 = 塑形失败。不要投入更多时间。 |
| 对交付后反馈做出反应 | 创造债务。失去干净状态。绕过塑形过程。 |
| 估算任务持续时间 | 估算隐藏了不确定性。改用山丘位置。 |
