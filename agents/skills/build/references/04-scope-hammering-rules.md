# 范围锤炼规则

> AI 代理在构建期间做出范围决策的参考手册。范围锤炼是强力质疑每项工作以将项目保持在时间盒内的纪律。

## 核心原则

固定时间，可变范围。截止日期永不移动。范围灵活调整。

---

## 决策框架

对于构建期间出现的每个任务、功能或需求，按顺序提问：

### 关卡 1：这是必须项吗？

```
这是功能正常工作所必需的吗？
  是 → 保留为必须项。进入关卡 2。
  否 → 标记为 ~（可选项）。进入关卡 3。
```

### 关卡 2：它符合时间预算吗？

```
这能在剩余时间内完成吗？
  是 → 执行。
  否 → 能简化以适应吗？
    是 → 简化并执行。
    否 → 升级：这真的是必须项，还是项目可以没有它就交付？
```

### 关卡 3：可选项分类

```
所有必须项完成后还有剩余时间吗？
  是 → 执行可选项。
  否 → 无需愧疚地删除。
```

---

## 范围锤炼问题

对出现的**任何**工作应用这些问题：

| # | 问题 | "否"意味着什么 |
|---|------|--------------|
| 1 | 这对新功能是必须的吗？ | 标记为可选项（~） |
| 2 | 没有这个我们能交付吗？ | 如果是，它是可选项 |
| 3 | 如果我们不做这个会怎样？ | 如果影响低，删除它 |
| 4 | 这是新问题还是已有问题？ | 如果是已有问题，用户已经在忍受——不紧急 |
| 5 | 这种情况发生的可能性有多大？ | 低概率 → 可选项 |
| 6 | 发生时哪些客户会看到它？ | 少数客户 → 可选项 |
| 7 | 它是核心（所有人使用）还是边缘情况？ | 边缘情况 → 可选项 |
| 8 | 发生时实际影响是什么？ | 低影响 → 可选项 |
| 9 | 这与目标受众的一致性如何？ | 低一致性 → 删除 |

---

## 任务分类

### 必须项
- 范围被认为"完成"所必需的
- 通过了上述所有范围锤炼问题
- 在范围上列为常规任务

### 可选项（标记为 `~`）
- 如果时间允许则完成
- 时间用完时无需愧疚地删除
- 通常永远不会构建——这没关系
- 可以应用于单个任务**或**整个范围

### 超出范围（来自方案包排除项）
- 在塑形期间明确排除
- 在构建期间不讨论
- 除非团队发现关键依赖，否则不重新考虑

## 范围削减模式

### 模式：简化实现
使用更简单的解决方案，而非理想方案，但仍然解决核心问题。
- 示例：不使用带展开/折叠的分组显示，而是显示带附加组标签的平面列表。

### 模式：减少表面积
支持更少的情况或更少的入口点。
- 示例：仅从主视图支持该功能，而非从每个子页面。

### 模式：推迟润色
交付可用功能，不进行视觉优化。
- 示例：默认浏览器样式，基本排版，无动画。

### 模式：放弃边缘情况
处理常见路径。让边缘情况优雅地失败或显示通用消息。
- 示例：支持单一时区而非时区转换。

### 模式：缩小受众
服务主要用户类型。其他用户类型稍后（或永远不会）获得该功能。
- 示例：仅为项目经理构建，而非所有团队成员角色。

---

## 比较点：基线

在决定是否削减范围时，始终与**基线**比较——客户今天拥有的。

```
这比客户目前拥有的更好吗？
  是 → 交付它。即使不完美。
  否 → 重新考虑削减。这可能是必须项。
```

削减范围**不是**降低质量。它是对**执行什么**有选择性，而非对**执行得多好**有选择性。代码质量、视觉设计质量、文案质量和交互性能保持高水准。问题只是：哪些事情对核心用例真正重要？

---

## QA 发现的问题

当 QA 在构建后期发现问题时：

1. **默认分类**：所有 QA 问题都是可选项
2. **分类**：团队评估严重性
3. **提升为必须项**：仅当对核心功能真正关键时
4. **组织**：将必须项问题移至相关范围的任务列表
5. **保留可选项**：如果时间用完，它们会被删除

---

## 延期决策（罕见）

超出分配会话的项目延期需要同时满足两个条件：

1. 剩余任务是通过每个范围锤炼问题后仍存活的真正必须项
2. **所有**剩余工作都是下坡的（没有未知因素，只有执行）

如果任何剩余工作是上坡的（仍有未知因素）→ **不要延期**。返回塑形。
