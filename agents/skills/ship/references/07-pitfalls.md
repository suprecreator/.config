# 代理的 Shape Up 陷阱

> Ryan Singer（Shape Up 创始人）在实际应用中识别的关键失败模式。这些陷阱对 AI 代理尤其危险，因为代理会按字面意思遵循指令，缺乏帮助人类纠正方向的机构直觉。

来源：Ryan Singer，"采用 Shape Up 时的常见陷阱"（2025 年 10 月）

---

## 陷阱 1：没有技术深度的塑形

### 陷阱所在

书中说塑形"主要是设计工作"。但 Basecamp 中进行塑形的人都有深厚的技术背景。当非技术人员进行塑形时，工作是**塑形不足的**——充满了在构建期间爆炸的未解答技术问题。

> 这是 Shape Up 采用的 #1 失败模式。

### 为何代理特别脆弱

代理在塑形功能时会默认描述*应该存在什么*（产品/设计语言），而不验证*它如何连接到实际代码库、数据模型、API 和基础设施*。代理可以产出读起来不错的提案，但包含隐藏的定时炸弹——从未验证过的技术可行性假设。

### 代理规则

1. **塑形必须包含技术分析。** 在撰写提案之前，代理必须检查实际代码库、数据模型和现有架构。

2. **输出是连接，而非样式。** 想象蓝图——墙在哪里，管道如何连接。而非油漆颜色或瓷砖选择。提案必须描述：
   - 功能在哪里连接到现有系统
   - 数据流向哪里
   - 哪些现有代码受影响
   - 需要哪些新的技术原语

3. **每个兔子洞都是定时炸弹。** 提案中任何未解决的兔子洞都**会**在构建期间爆炸。代理不能将兔子洞留为"TBD"——它们必须被修补、缩减或声明超出范围。

4. **高保真度最后。** 先构建粗糙和丑陋的。满足功能和交互需求。在最后一个会话中进行样式设计。这就像在建筑完成后才刷墙。

### 代理检查清单——技术深度

在最终确定任何提案之前：

- [ ] 已审查相关源代码和数据模型
- [ ] 已识别哪些现有模块/文件受影响
- [ ] 已确认技术方法在时间预算内可行（不仅仅是"可能"）
- [ ] 每个兔子洞都有解决方案（修补、缩减或超出范围）——零 TBD
- [ ] 解决方案描述了连接和接线，而非仅仅是 UI 概念

## 陷阱 2：框架化和塑形模糊

### 陷阱所在

书中没有清楚区分两个独立的工作步骤：

- **框架化**：定义问题、商业价值和期望结果
- **塑形**：在时间预算内设计技术解决方案

当这两者模糊时，项目会兜圈子、范围螺旋或在构建中途被取消（"闪亮物体综合症"），因为从来没有真正确信要解决什么问题。

### 为何代理特别脆弱

给定"我们需要功能 X"的代理会直接跳到设计解决方案，而不首先锁定要解决什么问题以及为什么重要。这产生了技术上合理但战略上没有锚点的提案——没有办法评估解决方案是否真正解决了正确的痛点，或者在时间紧张时做出范围权衡。

### 解决方案：将框架化与塑形分开

**框架化**（= 书中第 3 章"设定边界"）：
- 我们在解决什么问题？
- 为谁？
- 商业价值/期望结果是什么？
- 时间预算是多少？

**塑形**（= 书中第 4-5 章）：
- 技术解决方案是什么？
- 元素是什么？
- 风险是什么？

### 状态术语

使用这些明确的状态，而非模糊的术语：

| 状态 | 定义 |
|------|------|
| **候选项** | 尚未框架化的请求或想法。原材料。 |
| **框架通过** | 问题和结果已锁定。对我们在解决什么以及为什么达成一致。准备好塑形解决方案。 |
| **塑形通过** | 技术解决方案已定义。没有实质性未知因素。准备好交给构建者。 |

### 代理规则

1. **在塑形之前始终进行框架化。** 收到原始想法时，首先产出框架文档。在问题锁定之前不要设计解决方案。

2. **分开问题。** "我们在处理问题还是解决方案？"如果问题不够明确，停下来收紧它。不要用更好的解决方案来补偿。

3. **使用明确的检查点。** 代理必须在进行塑形之前确认框架通过。代理必须在产出最终提案之前确认塑形通过。

4. **清楚命名文档。** 使用"框架"表示问题/结果定义。使用"塑形"表示技术解决方案。避免"一页纸"或"规格"等模糊术语。

### 代理检查清单——框架化 vs. 塑形

塑形之前：
- [ ] 问题是具体的、基于故事的（而非通用的功能请求）
- [ ] 商业价值/期望结果已陈述
- [ ] 时间预算已设定
- [ ] 框架通过已确认（问题足够明确，可以设计解决方案）

提案之前：
- [ ] 解决方案具体解决了已框架化的问题
- [ ] 没有实质性技术未知因素
- [ ] 塑形通过已确认（构建者可以接手并知道该做什么）

## 陷阱 3：将项目工作与响应性工作混合

### 陷阱所在

如果已塑形的项目工作和响应性工作（错误、事故、紧急请求、第三方依赖）共享同一个队列和同一个团队，专注力就会被摧毁。太多的在制品，不清晰的优先级，无法衡量真实容量。

### 为何代理特别脆弱

管理构建的代理会遇到错误报告、紧急请求和外部阻碍。没有明确的分离规则，代理会将所有事情视为同等优先级——将响应性修复与已塑形的项目工作交织在一起，失去专注力，使构建面临风险。

### 代理规则

1. **完全分开流。** 已塑形的项目工作和响应性工作是具有不同追踪的不同流程。

2. **传入工作的分类规则：**

   | 类型 | 标准 | 处理方式 |
   |------|------|---------|
   | **已塑形的项目工作** | 有方案包。已被押注。有分配的会话。 | 在会话内执行。完全专注。 |
   | **紧急/着火** | 活跃事故。利益相关者不满。系统宕机。 | 单独处理。单独追踪。 |
   | **非紧急错误** | 不着火的错误。没有立即的利益相关者压力。 | 批量处理以后。不要混入活跃构建会话。 |
   | **依赖第三方** | 等待外部响应。代理无法控制时间线。 | 单独追踪。不要混入构建，因为你无法保证时间线。 |

3. **永远不要让响应性工作悄悄消耗会话时间。** 如果响应性工作在吃掉构建时间，明确提出。构建范围必须调整，或者响应性工作必须推迟。

4. **明确容量分配。** 如果团队（或代理）在项目和响应性工作之间分配时间，提前定义分配（例如，"80% 项目，20% 响应性缓冲"）。衡量实际情况与计划的对比。

---

## 总结：代理会陷入的三个陷阱

| 陷阱 | 代理行为 | 解决方案 |
|------|---------|---------|
| **塑形不足的工作** | 代理产出读起来不错但跳过技术验证的提案 | 要求代码库分析。每个兔子洞已解决。连接，而非样式。 |
| **框架化/塑形模糊** | 代理在锁定问题之前跳到解决方案 | 在任何解决方案设计之前强制执行框架通过检查点 |
| **混合工作流** | 代理将错误和紧急请求与构建工作交织在一起 | 分类所有传入工作。分开流。明确容量。 |

这些不是边缘情况——它们是 Shape Up 采用中最常见的失败模式。代理必须对所有三个都有明确的防护措施。
