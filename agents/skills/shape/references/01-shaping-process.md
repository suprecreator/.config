# 塑形过程

> AI 代理执行塑形角色的参考手册。塑形将原始想法转化为可押注的提案。

## 概述

塑形是在分配团队之前进行的预备工作，在独立的轨道上运行，与构建并行。塑形产出一份 Pitch（方案包）——一份具体到可以执行、但又足够粗糙以留有执行决策空间的文档。

**关键区别**：塑形有两个阶段，不能混淆（参见 `07-pitfalls.md`）：
- **框架化**（下面的步骤 1）——锁定问题、结果和时间预算。状态：**候选项 → 框架通过**。
- **塑形**（下面的步骤 2-4）——设计技术解决方案。状态：**框架通过 → 塑形通过**。

在问题锁定之前，永远不要设计解决方案。在技术方案经过验证之前，永远不要撰写提案。

## 步骤 1：框架化问题（设定边界）

### 设定时间预算

在设计任何内容之前，决定这个想法值得投入多少时间：

- **Small Batch（小批次）**：1 个会话（快速胜利，有限范围）
- **Medium Batch（中批次）**：2-3 个会话（适中范围，边界清晰）
- **Big Batch（大批次）**：4-5 个会话（重要功能，跨领域变更）
- 如果缩小后仍超过 5 个会话，则拆分为独立的部分

时间预算是**约束**，而非估算。它驱动设计，而非反过来。

**固定时间，可变范围**：时间是锁定的。范围灵活调整以适应时间。这迫使做出权衡决策，防止无限扩展。

### 缩小问题范围

将通用请求转化为具体的痛点：

1. **永远不要照单全收原始想法。** 默认回应："有意思，也许以后会做。"
2. **问："真正出了什么问题？"** ——从"我们需要一个日历"转变为"用户无法看到空闲时间段来安排帖子。"
3. **识别工作流程中断的具体时刻。**
4. **了解基线** ——用户今天在没有这个功能的情况下是怎么做的？
5. **拒绝大杂烩** ——没有单一定义问题的"重新设计 X"或"X 2.0"是无法塑形的。拆分为具体问题。

### 框架通过检查清单

在进行解决方案设计（元素）之前：

- [ ] 已捕获原始想法
- [ ] 已设定时间预算（小批次或大批次）
- [ ] 问题已缩小到具体的痛点
- [ ] 已陈述商业价值/期望结果
- [ ] 已拒绝或分解大杂烩
- [ ] **状态：框架通过** ——问题足够明确，可以设计解决方案

## 步骤 2：寻找元素

### 工作规则

- 独自工作或与一位可信赖的合作者（而非委员会）
- 保持正确的抽象层次：具体到可以取得进展，粗糙到可以广泛探索
- 回答：这在系统中适合放在哪里？如何到达它？关键组件是什么？它会带你去哪里？

### 技术 A：面包板（Breadboarding）

用于**流程和交互**。借鉴自电气工程。

仅三个元素：
1. **场所（Places）** ——屏幕、对话框、菜单（带下划线的名称）
2. **功能点（Affordances）** ——按钮、字段、操作（列在场所下方）
3. **连接线（Connection Lines）** ——功能点如何将用户从一个场所移动到另一个场所

规则：
- 仅使用文字，不使用图片
- 讨论流程，而非视觉效果
- 保持轻量——速度使探索成为可能

### 技术 B：粗笔草图（Fat Marker Sketches）

当**视觉布局是核心问题**时使用。

规则：
- 用粗线条绘制（防止添加细节）
- 展示粗略布局和空间关系
- 不使用线框图，不使用高保真元素

### 输出要求

元素必须：
- **具体**（不是"一个日历"，而是"带有事件点的双月网格视图，下方有议程列表"）
- **组件，而非任务** ——描述存在什么，而非要做什么
- **不完整** ——留有设计师做决策的空间

### 关卡检查

- 元素不是可交付成果。它们是粗糙的，对外人来说大多难以理解。
- 尚未做出承诺。工作可以在此时搁置或放弃。

## 步骤 3：去风险（风险和兔子洞）

### 目标

塑造概率分布：略有可能超出一个会话，但绝不超出时间预算的数倍。

### 过程

1. **慢动作走过用例** ——从头到尾追踪用户路径。揭示缺口。
2. **对每个元素提问：**
   - 这是否需要我们从未做过的技术工作？
   - 我们是否在未验证的情况下假设各部分能够配合？
   - 我们是否假设存在一个我们尚未验证的设计解决方案？
   - 是否有一个可能使团队停滞的艰难决策？

### 三种去风险行动

| 行动 | 使用时机 | 示例 |
|------|---------|------|
| **声明超出范围** | 用例不值得在此时间预算内支持 | "v1 不支持自定义域名" |
| **缩减** | 功能对核心价值不是必要的 | 移除非必要的 UI 元素 |
| **修补漏洞** | 现在需要做出的已知艰难决策，而非在构建期间 | 选择更简单的实现，接受权衡 |

### 技术验证

在撰写提案之前，如果不确定，向技术专家展示：

- **以探索性方式呈现**："这是我正在考虑的事情……"
- **正确的问题**："这在时间预算内可行吗？"（而非"这可行吗？"）
- **目标**：寻找定时炸弹
- **保持黏土湿润**：重新绘制元素，邀请替代方案

### 去风险状态检查清单（塑形通过）

- [ ] 解决方案元素定义为**连接**（连接、数据流、受影响的模块）——而非仅仅是 UI 概念
- [ ] 已审查实际代码库、数据模型和架构
- [ ] 兔子洞已修补或声明超出范围——**不允许有 TBD**（每个未解决的兔子洞都是定时炸弹）
- [ ] 在时间预算内验证了技术可行性（不仅仅是"可能"——而是在分配的会话内"可能"）
- [ ] 实现了细尾风险分布
- [ ] **状态：塑形通过** ——构建者可以接手并知道该做什么

## 步骤 4：撰写提案

### 五个必需要素

#### 1. 问题
- 展示现状为何失败的具体故事
- 建立判断解决方案的基线
- 没有问题陈述，就无法评估解决方案的适配性

#### 2. 时间预算
- 花多少时间（约束，而非估算）
- 不同的时间预算产生根本不同的解决方案
- 为所有人框定创意约束

#### 3. 解决方案
- 具有足够视觉支持以传达的已塑形元素
- 使用**嵌入式草图**（放置在现有 UI 上下文中的元素）或**注释粗笔草图**
- 保持粗糙——不使用线框图，不使用像素级精确的模型
- 添加免责声明："设计师可以自由寻找不同的方法"

#### 4. 兔子洞
- 已知的技术或设计风险及其处理方式
- 明确未处理的事项（"v1 的 URL 不会在自定义域名上"）
- 防止构建期间出现意外

#### 5. 排除项
- 故意排除的功能
- 故意不涵盖的用例
- 防止构建期间的范围蔓延

### 提案分发

- 异步发布，让押注桌成员可以自行阅读
- 允许技术专家评论以发现漏洞
- 保持押注桌会议简短——每个人提前阅读

## 塑形决策树

```
原始想法到来
  → 问题是否具体？
    否 → 缩小范围或作为大杂烩拒绝
    是 → 设定时间预算（小批次或大批次）
      → 寻找元素（面包板或粗笔草图）
        → 慢动作走过用例
          → 有兔子洞吗？
            是 → 修补、缩减或声明超出范围
            否 → 与技术专家验证
              → 撰写提案（5 个要素）
                → 发布给押注桌
```

## 反模式

| 反模式 | 为何失败 |
|--------|---------|
| 塑形中使用线框图 | 过于具体。扼杀设计师创造力。导致估算错误。 |
| 仅文字描述 | 过于抽象。团队无法做出权衡或了解范围。 |
| 大杂烩项目（"重新设计 X"） | 没有单一问题。无法确定范围、开始或完成。 |
| 先估算再设计 | 颠倒了约束。范围无限扩展。 |
| 承诺原始想法 | 未进行塑形。兔子洞和超支的高风险。 |
| 在委员会中塑形 | 太慢。需要 1-2 人之间的信任和默契。 |
| 跳过技术验证 | 定时炸弹在构建期间而非塑形期间被发现。 |
| **不分析代码库就塑形** | 提案读起来不错，但隐藏了技术未知因素。#1 失败模式。（参见 `07-pitfalls.md`） |
| **框架化之前就跳到解决方案** | 解决方案没有锚点。无法评估适配性或做出权衡。导致范围螺旋和取消的项目。 |
| **将兔子洞留为 TBD** | 每个未解决的兔子洞都会在构建期间爆炸。不允许有 TBD。 |
| **描述 UI 概念而非连接** | 提案展示了外观，但没有展示如何连接。构建者在构建中途发现缺失的管道。 |
